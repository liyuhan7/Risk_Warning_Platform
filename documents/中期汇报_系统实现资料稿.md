## 一、汇报核心结论

本项目目前已经从需求设计推进到可运行的后端主体实现阶段，形成了以 Spring Cloud 微服务（8 个模块）为基础、以 Kafka（6 个 Topic，3 分区）事件驱动为主线、以 Elasticsearch（4 个索引）/Milvus（3 个集合）/BERT（2 个模型）为智能分析支撑的合规风险评估链路。

当前系统已经具备以下中期成果：

1. 完成后端 8 个微服务模块工程搭建，涵盖网关、组织管理、处理、知识库、报告、通知、BERT 和公共模块，各模块通过 Nacos 注册发现。
2. 完成用户、企业、项目等基础业务对象建模（8 张 PostgreSQL 表 + 触发器 + 索引 + 约束），为评估任务提供完整业务上下文。
3. 完成三阶段分片文件上传（初始化→分片→确认）、Redis 上传状态记录（3 类 Redis Key）、后台 `ExecuteQueueTask` 定时合并和 Kafka `behavior_processing_tasks` 任务触发。
4. 完成文档解析（`FileScanner` + `ContentExtractor` + `parallelStream` 并行处理）、文本片段抽取、Spring Batch 行为构造（`LineProcessor` → `LineRangeItemWriter`）和 ES `t_behavior` 索引入库。
5. 完成 BERT 向量化（`bert-base-chinese`，768 维）与多任务分类服务（`chinese-roberta-wwm-ext`，4 头 126 类）接入，通过 Flask 提供 6 个 REST API，为行为、指标、法规提供语义表达。
6. 完成知识库向量化与 ES KNN / Milvus 语义检索基础能力，支持相似指标和相似法规召回（Top-200，支持行业/地域/维度多条件过滤）。
7. 完成行为-指标-法规三元匹配（相似度阈值过滤 + 三层法规权重 + 定性/定量/兜底三类计算器）和指标得分计算雏形。
8. 完成风险触发（scoreRatio < 0.5）、报告聚合（5 类统计分布）和 Netty WebSocket 通知推送基础闭环。

可以用一句话概括当前实现：

```text
企业上传材料后，系统能够异步解析文档、抽取行为、完成分类和向量化，
再将行为与指标、法规进行语义匹配，计算指标结果，生成风险报告并通知用户。
```

## 二、系统总体实现架构

### 1. 工程结构

项目采用 Maven 父子模块结构，父工程统一管理依赖版本和公共配置。当前仓库主要包括以下 8 个子模块，各模块有明确的端口分配：

| 模块 | 端口 | 主要职责 |
| --- | --- | --- |
| `risk-warning-common` | — | 公共实体、枚举、DTO、消息体、工具类、异常处理 |
| `risk-warning-gateway` | 8088 | API 网关、统一路由、CORS 跨域、JWT 鉴权 |
| `risk-warning-org` | 8095 | 用户认证、企业管理、项目管理、分片上传、上传队列消费 |
| `risk-warning-processing` | 8084 | 文档解析、行为抽取、Spring Batch、三元匹配与指标计算 |
| `risk-warning-knowledge` | 8089 | 知识库向量化、Milvus 集合管理、ES/Milvus 语义检索 |
| `risk-warning-report` | 8093 | 评估报告聚合、风险触发与等级评定、风险分布统计 |
| `risk-warning-notification` | 8091 | Kafka 通知消费、Netty WebSocket 连接管理、实时推送 |
| `risk-warning-bert` | 8090 | BERT 向量化与分类服务的 Java 封装、Python 进程管理 |

父 POM 统一管理核心依赖版本：Spring Boot 2.6.13、Spring Cloud 2021.0.5、Elasticsearch Java Client 8.11.0、Milvus SDK 2.3.5、PostgreSQL 42.3.1、Redis Lettuce、OkHttp 4.9.3、Spring Kafka、Spring Batch、Netty 4.1。

代码依据：

- `pom.xml`：定义 8 个 `<module>` 子模块声明，统一 `<dependencyManagement>` 管理所有第三方依赖版本。
- `risk-warning-common`：集中维护公共 PO（`User`、`Enterprise`、`Project`、`Behavior`、`Indicator`、`Regulation`、`IndicatorResult`、`Assessment`）、DTO、枚举、Kafka 消息体和工具类，减少跨服务重复定义。

### 2. 技术架构

系统采用“同步接口 + 异步任务 + 智能检索”的组合架构。

同步接口主要处理用户登录、企业管理、项目管理、文件上传初始化、报告查询等即时请求（响应时间 < 200ms）。耗时任务（文档解析、行为抽取、向量化、指标计算、报告聚合）通过 Redis 队列与 Kafka 事件进入后台链路，由专用线程池（`FileProcessTaskThreadPool`、`BehaviorProcessTaskThreadPool`）异步执行。

核心中间件及版本分工如下：

| 技术组件 | 版本 | 在系统中的作用 |

| Nacos | 2.x | 服务注册发现与配置中心管理 |

| Redis | 6.2 | 文件上传分片状态记录、上传任务信息缓存、确认上传队列（端口 6379） |

### 3. 网关路由与统一鉴权

网关服务 (`risk-warning-gateway:8088`) 负责统一接入所有业务接口。`application.yml` 中配置了 5 条 Nacos 负载均衡路由规则：

| 路由前缀 | 目标服务 | 说明 |
| --- | --- | --- |
| `/api/org/**` | `lb://risk-warning-org` | 用户/企业/项目/文件管理 |
| `/api/processing/**` | `lb://risk-warning-processing` | 文档处理/行为分析 |
| `/api/knowledge/**` | `lb://risk-warning-knowledge` | 向量化/知识检索 |
| `/api/report/**` | `lb://risk-warning-report` | 报告查询 |
| `/api/notification/**` | `lb://risk-warning-notification` | WebSocket 通知（含 WS 升级） |

网关层通过 `AuthFilter`（实现 `GlobalFilter`）实现 JWT 鉴权过滤器：

- **放行路径**：`/user/login`、`/user/register` 等登录注册接口。
- **鉴权逻辑**：从请求头提取 `Authorization: Bearer <token>`，调用 `JwtUtils.validateToken()` 校验。
- **JWT 配置**：签名密钥 `riskWarningPlatformSecretKey2024ForJWTTokenGeneration`，有效期 24 小时。
- **异常处理**：Token 缺失返回 401 `"未提供认证令牌"`，Token 无效或过期返回 401 `"令牌无效或已过期"`。

代码依据：

- `risk-warning-gateway/src/main/resources/application.yml` — 路由配置与 CORS 全局设置。
- `risk-warning-gateway/src/main/java/com/riskwarning/gateway/filter/AuthFilter.java` — JWT 鉴权过滤器。
- `risk-warning-common/src/main/java/com/riskwarning/common/utils/JwtUtils.java` — JWT 生成与校验。

汇报表达：

```text
网关不仅承担请求转发，也承担统一认证入口。
这样各个微服务可以专注于业务逻辑，登录注册之外的接口都通过 Bearer Token 保护。
```

## 三、基础业务管理模块实现

### 1. 用户管理

用户管理模块基于 `t_user` 表，实现了注册、登录、用户资料查询和更新等能力。

**数据库表结构**（`t_user`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGSERIAL | 主键，自增 |
| `email` | TEXT UNIQUE | 邮箱，唯一标识 |
| `password` | TEXT | 加密后的密码 |
| `full_name` | TEXT | 用户全名 |
| `avatar_url` | TEXT | 头像 URL |
| `created_at` | TIMESTAMPTZ | 创建时间（自动） |
| `updated_at` | TIMESTAMPTZ | 更新时间（触发器自动维护） |

注册流程（`UserController.register()` → `UserServiceImpl.register()`）：

1. 接收 `email`、`password`、`fullName`。
2. 检查邮箱是否已存在（`userRepository.findByEmail()`）。
3. 调用 `PasswordUtils.encode()` 对密码进行 BCrypt 加密。
4. 保存 `User` 实体到 `t_user` 表。
5. 返回 `UserResponse` DTO。

登录流程（`UserController.login()` → `UserServiceImpl.login()`）：

1. 根据邮箱查询用户。
2. 调用 `PasswordUtils.matches()` 校验密码。
3. 调用 `JwtUtils.generateToken(userId, email)` 生成 JWT（24h 有效期）。
4. 返回 `LoginResponse`（含 token、userId、email、fullName）。

代码依据：

- `risk-warning-org/.../controller/UserController.java`
- `risk-warning-org/.../service/impl/UserServiceImpl.java`
- `risk-warning-common/.../dto/LoginResponse.java`
- `risk-warning-common/.../utils/PasswordUtils.java`

汇报表达：

```text
用户模块是系统身份体系的入口。
登录后生成 JWT，后续请求由网关统一校验，从而支撑跨服务访问控制。
```

## 四、文件上传与异步任务链路实现

### 1. 分片上传设计

系统采用三阶段文件上传流程：

```text
初始化上传 (initUpload) -> 分片上传 (uploadChunk) -> 确认上传 (confirmUpload)
```

**阶段一：初始化上传**（`FileController.initUpload()` → `FileServiceImpl.initUpload()`）

系统校验：

- 文件是否重复（MD5 校验）。
- 项目上传文件数量是否超过限制（默认 50 个）。
- 文件类型是否支持（PDF、DOC、DOCX、XLS、XLSX、TXT）。
- 文件大小是否超过限制（默认 100MB）。
- 分片数量是否超过限制（默认 1000 片）。

通过后生成 `uploadId`（UUID），并写入 Redis：

| Redis Key | 类型 | 内容 |
| --- | --- | --- |
| `REDIS_KEY_FILE:{uploadId}` | String | 上传任务基本信息（文件名、总分片数等） |
| `REDIS_KEY_FILE_UPLOAD_INFO:{projectId}:{uploadId}` | Hash | 项目维度的上传详情 |

代码依据：

- `FileController.initUpload()`
- `FileServiceImpl.initUpload()`
- `RedisKey.REDIS_KEY_FILE`
- `RedisKey.REDIS_KEY_FILE_UPLOAD_INFO`

### 2. 分片状态记录

分片上传时（`FileServiceImpl.uploadChunk()`），系统将分片写入临时目录（`Constants.TEMP_DIR`），并用 Redis Set 记录已上传分片索引：

| Redis Key | 类型 | 内容 |
| --- | --- | --- |
| `REDIS_KEY_UPLOAD_CHUNKS:{uploadId}` | Set | 已上传分片索引集合 |

容错机制：如果分片写入失败，系统从 Redis Set 中移除对应分片索引，确保状态与实际文件一致。

代码依据：

- `FileServiceImpl.uploadChunk()`
- `FileUtils.transferFile()`
- `RedisKey.REDIS_KEY_UPLOAD_CHUNKS`

### 3. 确认上传与后台合并

确认上传时（`FileServiceImpl.confirmUpload()`），系统检查所有分片是否完整（Set 大小 == 总分片数）。完整后不直接执行合并，而是向 Redis 确认队列写入 `UploadConfirmDto`（JSON 序列化）：

| Redis Key | 类型 | 内容 |
| --- | --- | --- |
| `REDIS_KEY_FILE:{projectId}` | List | 待处理的确认上传任务队列 |

后台任务 `ExecuteQueueTask.consumeTransferQueue()` 以 `@Scheduled` 定时轮询（默认 2 秒间隔），从 Redis 队列 `BLPOP` 取出确认任务：

```text
步骤 1：合并临时分片文件（FileUtils.mergeFiles()）
步骤 2：保存 ProjectFile 记录到 t_project_file 表
步骤 3：创建 Assessment 待评估记录（status=TO_BE_ASSESSED）到 t_assessment_result 表
步骤 4：构造 BehaviorProcessingTaskMessage（type=FILE_UPLOAD），发送到 Kafka topic behavior_processing_tasks
步骤 5：清理 Redis 缓存（uploadId 相关 key）和临时分片文件
```

代码依据：

- `FileServiceImpl.confirmUpload()`
- `ExecuteQueueTask.consumeTransferQueue()`
- `ProjectFile`（`t_project_file` 表：`id`、`project_id`、`user_id`、`file_paths` JSONB）
- `Assessment`（`t_assessment_result` 表：`id`、`project_id`、`assessment_date`、`overall_score`、`overall_risk_level`、`details` JSONB、`status`）
- `BehaviorProcessingTaskMessage`（字段：`messageId`、`type`、`userId`、`projectId`、`assessmentId`、`filePaths`）
- `KafkaUtils.sendMessage()`

**Kafka 消息格式**（`BehaviorProcessingTaskMessage`）：

```json
{
  "messageId": "uuid",
  "type": "FILE_UPLOAD",
  "userId": 1,
  "projectId": 100,
  "assessmentId": 200,
  "filePaths": ["/path/to/file1.pdf", "/path/to/file2.docx"]
}
```

汇报表达：

```text
文件上传模块没有把耗时处理放在接口请求中。
上传确认后先进入 Redis 队列，由后台线程合并文件并发送 Kafka 消息，
从而把文件传输、文件落库和后续智能处理解耦。
```

## 五、文档解析、行为抽取与行为入库实现

### 1. 文档处理流程

处理服务 (`risk-warning-processing:8084`) 通过 `MessageTask.onMessage()` 监听 Kafka topic `behavior_processing_tasks`（groupId=`test-consumer`），收到 `FILE_UPLOAD` 类型消息后提交到 `FileProcessTaskThreadPool` 线程池异步执行。

处理过程（`DocumentProcessingService.processDocument()`）：

```text
步骤 1：通过 FileGetter 获取文件（支持 URL 和本地路径两种来源）
步骤 2：获取文件元数据（文件名、大小、类型）
步骤 3：文件格式校验（PDF/Word/Excel）
步骤 4：通过 FileScanner 按页扫描文档（支持 parallelStream 并行处理）
步骤 5：通过 ContentExtractor 从每页抽取有效文本片段（TextSegment）
步骤 6：将文本片段写入内部 .txt 中间文件（UTF-8 编码，每行一个行为描述）
```

代码依据：

- `DocumentProcessingService.processDocument(projectId, urls, localPaths)` — 返回 `List<String>` 内部文件路径列表。
- `DocumentProcessingService.process(projectId, uploadUrls, uploadPaths)` — 生成 `DocumentProcessingResult`。
- `FileGetter` — 统一获取远程/本地文件。
- `FileScanner` — `scanPages()` 按页扫描，`parallelStream()` 并行加速。
- `ContentExtractor` — 从页面提取文本片段（`extractTextSegments()`）。

**关键设计决策**：

- 使用 `parallelStream()` 对多页面并行处理，利用多核 CPU 加速。
- 抽取结果写入 `.txt` 中间文件（路径格式：`Constants.INTERNAL_DIR/{projectId}/behavior_{timestamp}.txt`），为后续 Spring Batch 提供标准化输入。
- 文档处理失败时记录日志但不阻塞整体流程。

### 2. Spring Batch 行为构造

文档处理完成后，`MessageTask` 调用 `BatchJob.runBatchJob()` 启动 Spring Batch 作业，将中间文本文件中的每一行转换为 `Behavior` 对象。

**Batch 作业配置**（`BatchConfig`）：

| 组件 | 实现类 | 作用 |
| --- | --- | --- |
| Partitioner | `LineRangePartitioner` | 按文件行范围分区，支持多线程并行处理 |
| ItemReader | `LineRangeItemReader` | 按分区读取指定行范围的文本行 |
| ItemProcessor | `LineProcessor` | 将文本行转换为 `Behavior` 对象 |
| ItemWriter | `LineRangeItemWriter` | 将 `Behavior` 批量写入 Elasticsearch |
| JobListener | `JobListener` | 作业完成后触发指标计算任务 |

`LineProcessor.process()` 的核心逻辑：

1. 过滤空文本和纯空白行。
2. 生成行为 ID（`StringUtils.generateId()`）。
3. 绑定 `projectId`（从 JobParameters 获取）。
4. 将文本行写入 `description` 字段。
5. 初始化行为字段：`type`（待分类）、`dimension`（待分类）、`tags`（空）、`status`（`PENDING`）、`behaviorDate`（当前时间）。

### 3. 行为分类、向量化和 ES 入库

`LineRangeItemWriter.write()` 在真正写入 ES 前，为每个 `Behavior` 补充两类智能信息：

**步骤 1：行为分类**（`ClassifierClient.classifyBatch()`）

调用 Python BERT 服务 `/classify/batch` 接口，请求体格式：

```json

  "items": [
    {"text": "行为描述文本", "input_type": "behavior"}

```

返回分类结果，用于填充 `Behavior` 的 `tags`（46 类标签）、`type`（定性/定量）、`dimension`（6 类风险维度）。

**步骤 2：行为向量化**（`VectorizationClient.batchVectorize()`）

调用 Python BERT 服务 `/encode` 接口，将 `description` 文本转为 768 维向量，存入 `descriptionVector` 字段。

**步骤 3：ES Bulk 写入**

通过 `ElasticsearchClient.bulk()` 将行为批量写入 ES 索引 `t_behavior`。ES Mapping 关键字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |

| `dimension` | keyword | 风险维度 |
| `tags` | keyword | 分类标签 |
| `status` | keyword | 行为状态 |

### 2. 文本向量化

BERT 向量化完整流程：

```text
输入文本列表
  → AutoTokenizer.from_pretrained("bert-base-chinese")
    （padding=True, truncation=True, max_length=512）
  → AutoModel.from_pretrained("bert-base-chinese")
  → model.eval() 推理模式 + torch.no_grad()
  → outputs.last_hidden_state[0][0]  ← 取 [CLS] token 向量
  → .cpu().numpy().tolist()
  → 768 维 float 向量输出
```

**模型加载**（`load_model()`，启动时执行一次）：

```python
model_name = os.getenv("BERT_MODEL_NAME", "bert-base-chinese")
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModel.from_pretrained(model_name)
model.eval()
```

**关键实现要点**：

- 模型名称通过环境变量 `BERT_MODEL_NAME` 配置，默认 `bert-base-chinese`，可灵活切换。
- 最大序列长度 512 tokens，超长文本自动截断。
- `model.eval()` + `torch.no_grad()` 确保推理模式（关闭 Dropout/梯度计算）。
- 取 `[CLS]` token 的 hidden state 作为句子级向量表示。
- 全局变量存储模型，避免每次请求重新加载（模型加载约需 30-120 秒）。

#### 向量化模型选型与优化分析

当前向量化模型使用通用预训练模型 `bert-base-chinese`，其预训练任务是掩码语言建模（MLM），并非为语义相似度优化。在检索和匹配场景中，存在以下可优化方向：

| 问题 | 当前状态 | 影响 |
|------|---------|------|
| 模型选型 | `bert-base-chinese`（MLM 预训练） | 通用 MLM 预训练，未针对语义嵌入优化 |
| 池化方式 | `[CLS]` 向量 | CLS token 预训练偏置不适合做句子表示 |
| 归一化 | 未做 L2 归一化 | Java 端余弦相似度计算需要单位向量 |
| 推理方式 | 逐条编码（for 循环） | 无法利用 GPU 批量并行加速 |

建议后续替换为嵌入专用模型。以下为推荐方案对比：

| 推荐模型 | 维度 | C-MTEB 得分 | 说明 |
|---------|------|-----------|------|
| `BAAI/bge-base-zh-v1.5` | 768 | 63.13 | 与当前 ES mapping 完全兼容，零代码改动 |
| `BAAI/bge-large-zh-v1.5` | 1024 | 64.53 | 效果最优，但需更新向量维度 |
| `BAAI/bge-m3` | 1024 | 多语言 SOTA | 支持 Dense+Sparse+ColBERT 三模式，8192 tokens |
| `Alibaba-NLP/gte-Qwen2-1.5B-instruct` | 1536 | 67.65（中文） | LLM 基座嵌入模型，语义理解力更强 |

其中 `bge-base-zh-v1.5` 为最推荐方案——768 维与现有 ES mapping 完全兼容，使用 mean pooling + L2 归一化，且代码已通过 `BERT_MODEL_NAME` 环境变量配置模型，只需切换环境变量即可启用。

### 3. 多任务分类

## 八、行为-指标-法规三元语义匹配实现

### 1. 模块目标

智能匹配模块的目标是建立三类对象之间的关联关系：

```text
企业行为 (Behavior) → 合规指标 (Indicator) → 法规依据 (Regulation)
```

这个模块是系统风险评估的核心，因为风险不是直接从文本中得出，而是通过行为与指标、法规之间的语义关联计算出来。

### 2. 指标计算任务入口

文档处理和行为入库完成后，`JobListener.afterJob()` 发送 `IndicatorCalculationTaskMessage` 到 Kafka topic `indicator_calculation_tasks`。处理服务的 `MessageTask` 监听该主题（groupId=`indicator-calculation-consumer`），提交到 `BehaviorProcessTaskThreadPool` 后调用：

```java
behaviorProcessingService.processProjectBehaviors(userId, projectId, assessmentId)
```

代码依据：

- `risk-warning-processing/task/MessageTask.java` — `@KafkaListener(topics = "indicator_calculation_tasks")`
- `BehaviorProcessingService.processProjectBehaviors()`

### 3. 候选召回

核心常量（定义在 `BehaviorProcessingService` 中）：

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `REG_APPLICABILITY_THRESHOLD` | 0.15 | 行为-法规相似度最低阈值 |
| `REG_TO_INDICATOR_THRESHOLD` | 0.2 | 法规-指标相似度最低阈值 |
| `BEHAVIOR_VECTOR_FIELD` | `description_vector` | 行为 ES 向量字段名 |
| `INDICATOR_VECTOR_FIELD` | `name_vector` | 指标 ES 向量字段名 |
| `REGULATION_VECTOR_FIELD` | `full_text_vector` | 法规 ES 向量字段名 |
| `CANDIDATE_FETCH_SIZE` | 200 | 候选召回数量 |

系统从 ES 中获取项目下所有行为（`fetchBehaviors()`），然后对每个行为通过 ES KNN 查询召回候选：

| 召回对象 | 方法 | 查询向量 | 索引 |
| --- | --- | --- | --- |
| 候选指标 | `fetchTopIndicators()` | `behavior.descriptionVector` | `t_indicator`（字段 `name_vector`） |
| 候选法规 | `fetchTopRegulations()` | `behavior.descriptionVector` | `t_regulation`（字段 `full_text_vector`） |

召回方式：使用 Elasticsearch `script_score` 查询 + `cosineSimilarity` 函数进行 KNN 向量检索，获取 Top-200 候选。

代码依据：

- `fetchBehaviors()` — 从 ES `t_behavior` 索引获取行为列表
- `fetchTopIndicators()` — ES KNN 召回候选指标
- `fetchTopRegulations()` — ES KNN 召回候选法规

### 4. 相似度与权重计算

系统对候选结果进行进一步判断（`computeMappingFromCandidates()`）：

```text
步骤 1: 计算 行为-法规 相似度（SimilarityCalculator.scoreBehaviorToTargetDefault()）
        → 如果 < REG_APPLICABILITY_THRESHOLD (0.15)，过滤该法规
步骤 2: 计算 法规-指标 相似度（SimilarityCalculator.scoreRegToIndicatorDefault()）
        → 如果 < REG_TO_INDICATOR_THRESHOLD (0.2)，过滤该指标
步骤 3: 将行为-法规相似度 × 法规-指标相似度 → 合成影响力得分
步骤 4: 对通过筛选的法规计算三层权重：
        ├── hierarchyWeight: 法规层级权重（RegWeightCalculator.getHierarchyWeight()）
        │     法律 > 行政法规 > 部门规章 > 地方性法规 > 规范性文件
        ├── timelinessWeight: 时效性权重（RegWeightCalculator.getTimelinessWeight()）
        │     现行有效 > 即将实施 > 已修订 > 已废止
        └── similarityWeight: 相似度权重（基于行为-法规余弦相似度归一化）
```

**相似度计算方式**：综合使用加权余弦相似度（基于 BERT 向量）与 Jaccard 系数（基于关键词集合），为静态手工公式。

代码依据：

- `computeMappingFromCandidates()`
- `SimilarityCalculator.scoreBehaviorToTargetDefault()`
- `SimilarityCalculator.scoreRegToIndicatorDefault()`
- `RegWeightCalculator.getHierarchyWeight()`
- `RegWeightCalculator.getTimelinessWeight()`

### 5. 定性/定量规则计算

系统根据法规和行为的类型，选择不同计算方式（`computeRegulationScore()`）：

| 类型 | 计算器 | 计算逻辑 |
| --- | --- | --- |
| 定量数据 | `QuantitativeCalculator.computeQuantitativeScore()` | 基于 `calculation_rule.range_rule`（min/max value + calculation_method），将行为的 `quantitative_data` 映射到得分 |
| 定性数据 | `QualitativeCalculator.computeQualitativeScore()` | 基于 `calculation_rule.binary_rule`（condition + true_score/false_score），判断行为是否符合条件 |
| 缺少明确规则 | `FallbackCalculator` | 基于相似度得分兜底计算，确保每个指标都能产出分数 |

代码依据：

- `computeRegulationScore()`
- `getFallback()`
- `QuantitativeCalculator` — 定量计算器
- `QualitativeCalculator` — 定性计算器
- `FallbackCalculator` — 兜底计算器

### 6. 指标结果保存

系统不会每处理一个行为就立即落库，而是先把计算结果收集到线程安全结构中：

| 数据结构 | 用途 |
| --- | --- |
| `ConcurrentHashMap<String, IndicatorResult>` | 按指标 ES ID 去重聚合多个行为的计算结果 |
| `CopyOnWriteArrayList<IndicatorResult>` | 线程安全的指标结果列表 |
| `CountDownLatch` | 等待所有行为的并行处理完成 |
| `AtomicInteger` | 原子计数器，跟踪处理进度 |

所有行为处理完成后，统一调用 `batchSaveIndicatorResults()` 批量保存指标结果到 `t_indicator_result` 表。

**数据库存储**（`t_indicator_result` 表）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `project_id` | BIGINT FK | 关联项目 |
| `assessment_id` | BIGINT FK | 关联评估 |
| `indicator_es_id` | TEXT | ES 中指标 ID |
| `indicator_name` | TEXT | 指标名称（冗余） |
| `indicator_level` | INTEGER | 指标层级 |
| `dimension` | TEXT | 风险维度 |
| `calculated_score` | NUMERIC | 计算得分（≥0） |
| `max_possible_score` | NUMERIC | 最大可能得分（>0） |
| `used_calculation_rule_type` | TEXT | 使用的规则类型（`binary`/`range`） |
| `calculation_details` | JSONB | 计算过程详情（规则、中间值） |
| `matched_behaviors_ids` | TEXT[] | 匹配的行为 ES ID 列表 |
| `risk_triggered` | BOOLEAN | 是否触发风险 |
| `risk_status` | ENUM | 风险是否已评估 |

代码依据：

- `processProjectBehaviors()`
- `batchSaveIndicatorResults()`
- `IndicatorResultRepository` — JPA Repository，继承 `JpaRepository<IndicatorResult, Long>`

## 九、风险评估与报告聚合实现

### 1. 评估完成事件

指标计算全部完成后，`BehaviorProcessingService.completeAssessmentIfNeeded()` 通过 `CountDownLatch.await()` 确认所有行为处理完毕，然后发送 `AssessmentCompletedEventMessage` 到 Kafka topic `assessment_completed_events`。

报告服务 (`risk-warning-report:8093`) 的 `MessageTask` 监听该主题（groupId=`test-consumer`），收到消息后调用：

```java
assessmentService.aggregateInformation(userId, projectId, assessmentId)
```

**Kafka 消息流**（完整链路）：

```text
behavior_processing_tasks (3 分区)
  → 文档处理 + Batch + ES 入库
  → indicator_calculation_tasks (3 分区)
    → 三元匹配 + 指标计算
    → assessment_completed_events (3 分区)
      → 报告聚合 + 风险触发
      → notification_tasks (3 分区)
        → WebSocket 推送
```

代码依据：

- `BehaviorProcessingService.completeAssessmentIfNeeded()`
- `risk-warning-report/task/MessageTask.java` — `@KafkaListener(topics = "assessment_completed_events")`
- `AssessmentServiceImpl.aggregateInformation()`

### 2. 风险触发逻辑

报告服务读取该评估下所有 `IndicatorResult`，逐个计算：

```text
scoreRatio = calculatedScore / maxPossibleScore
```

风险判定规则：

| 条件 | 风险等级 | 说明 |
| --- | --- | --- |
| `scoreRatio ≥ 0.8` | 无风险 | 指标达标 |
| `0.5 ≤ scoreRatio < 0.8` | 低风险 | 需关注 |
| `0.3 ≤ scoreRatio < 0.5` | 中风险 | 需整改 |
| `scoreRatio < 0.3` | 高风险 | 严重违规 |

当 `scoreRatio < 0.5` 时，系统触发风险记录，写入 ES `t_risk` 索引。风险记录包含：

- `projectId`：项目 ID
- `assessmentId`：评估 ID
- `riskName`：风险名称
- `dimension`：风险维度
- `riskLevel`：风险等级（`RiskLevelEnum`：LOW / MEDIUM / HIGH / CRITICAL）
- `disposeStatus`：处置状态（`RiskStatusEnum.TO_BE_DISPOSED`）
- `relatedIndicators`：相关指标列表
- `relatedBehaviors`：相关行为列表
- `relatedRegulations`：相关法规列表

代码依据：

- `AssessmentServiceImpl.aggregateInformation()`
- `RiskLevelEnum.getByScoreRatio()` — 得分比例到风险等级的映射
- `RiskStatusEnum.TO_BE_DISPOSED`

### 3. 报告聚合

报告服务聚合以下内容（`ReportServiceImpl`）：

| 聚合内容 | 计算方法 | VO 类 |
| --- | --- | --- |
| 总体得分 | 所有指标 `calculatedScore` 的加权平均 | `AssessmentGeneralDetails.overallScore` |
| 总体风险等级 | 根据高/中/低风险数量综合判定 | `AssessmentGeneralDetails.overallRiskLevel` |
| 风险概览 | 统计高/中/低风险的数量 | `RiskDistribution`（`highCount`/`mediumCount`/`lowCount`） |
| 维度分布 | 按 `dimension` 分组统计风险数量 | `List<RiskVO>`（`dimension` + `count`） |
| 指标分布 | 按得分区间（0-30/30-50/50-80/80-100）统计指标数量 | `IndicatorDistributionVO`（含 `ScoreRatioDistributionItemVO` 列表） |

聚合后的详情序列化为 JSON，保存到 `Assessment.details`（PostgreSQL JSONB 字段），避免每次查询重复计算。

**报告查询 API**（`ReportController`）：

| 端点 | 返回 |
| --- | --- |
| `GET /indicatorResult/{assessmentId}` | 指标计算结果列表 |
| `GET /risk?assessmentId={id}` | 风险记录列表 |
| `GET /general/{assessmentId}` | 总体评估详情（含分布统计） |

代码依据：

- `ReportServiceImpl.assembleGeneral()` — 组装总体评估
- `ReportServiceImpl.assembleIndicatorResult()` — 组装指标分布
- `AssessmentGeneralDetails`、`AssessmentDetailVO`、`IndicatorDistributionVO`、`RiskDistribution`、`RiskVO`

汇报表达：

```text
报告模块把底层指标计算结果转化为用户可以理解的风险视图。
它不仅保存风险明细，还聚合总体得分、风险等级、维度分布和指标分布，
为前端仪表盘和报告展示提供直接数据。
```

### 2. WebSocket 推送

通知服务 (`risk-warning-notification:8091`) 基于 Netty 实现 WebSocket 实时推送。

**架构组件**：

| 组件 | 类名 | 作用 |
| --- | --- | --- |
| 服务器启动 | `NotificationNettyRunner` | Spring Boot 启动后初始化 Netty 服务器（端口 8091） |
| 服务器 | `NotificationServer` | Netty `ServerBootstrap`，绑定 `/api/notification/ws` 路径 |
| 帧处理 | `NotificationWebSocketHandler` | 处理 WebSocket 帧（文本帧、二进制帧、握手、关闭） |
| 连接管理 | `WebSocketChannelManager` | 维护用户-通道双向映射 |
| 消息消费 | `NotificationMessageTask` | 消费 Kafka `notification_tasks` 主题 |

**`WebSocketChannelManager` 双向映射**：

| 映射 | 类型 | 作用 |
| --- | --- | --- |
| `USER_CHANNEL_MAP` | `ConcurrentHashMap<Long, Channel>` | 根据 userId 找到在线 WebSocket 连接 |
| `CHANNEL_USER_MAP` | `ConcurrentHashMap<Channel, Long>` | 连接断开时反查 userId 清理映射 |

**连接流程**：

```text
1. 客户端连接 ws://localhost:8091/api/notification/ws
2. 客户端发送绑定消息: {"type": "bind", "userId": 123}
3. NotificationWebSocketHandler 调用 channelManager.bindUser(userId, channel)
4. WebSocketChannelManager 建立 userId ↔ Channel 双向映射
```

**推送流程**：

```text
1. NotificationMessageTask 监听 Kafka notification_tasks（groupId=notification-consumer）
2. 收到消息后构造前端 JSON:
   {
     "type": "notification",
     "notificationType": "ASSESSMENT_COMPLETED",
     "title": "评估完成",
     "content": "项目XXX合规评估已完成，风险等级：中",
     "projectId": 123,
     "assessmentId": 456,
     "timestamp": "2024-01-01T12:00:00Z",
     "extraData": {"riskLevel": 2, "overallScore": 72.5}
   }
3. channelManager.sendMessageToUser(userId, jsonText)
4. 通过 channel.writeAndFlush(new TextWebSocketFrame(text)) 推送
```

**离线处理**：如果用户在 `USER_CHANNEL_MAP` 中不存在（不在线），消息进入离线存储预留逻辑（TODO：Redis 离线消息队列）。

代码依据：

- `NotificationMessageTask.onNotificationMessage()` — `@KafkaListener(topics = "notification_tasks", groupId = "notification-consumer")`
- `WebSocketChannelManager.sendMessageToUser()`
- `NotificationServer` — Netty 管道配置
- `NotificationNettyRunner` — Spring Boot 生命周期集成

汇报表达：

```text

报告聚合完成后，用户不需要手动刷新查询，系统可以通过 Kafka 事件和 WebSocket 长连接主动通知评估完成。
```

```text

    → Kafka: behavior_processing_tasks (3 分区, groupId=test-consumer)
```

```ts
}
```

### 4. 状态管理与 WebSocket 集成

`stores/user.ts`（Pinia）管理全局用户状态，核心逻辑：

- **登录**：调用 API → 拼接 `Bearer token` → `sessionStorage` 持久化 → 自动连接 WebSocket。
- **注册**：调用 API → 成功后跳转登录页。
- **退出**：主动断开 WebSocket → 清除 token/user → 跳转登录页。
- **初始化**：`initUser()` 在 Store 创建时自动从 `sessionStorage` 恢复用户信息，若 token 有效则自动重连 WebSocket。

`utils/websocket.ts` 封装了完整的 WebSocket 连接管理：

| 能力 | 实现 |
| --- | --- |
| 连接地址 | 默认 `ws://localhost:9090/ws`，支持 `VITE_WEBSOCKET_URL` 环境变量 |
| 用户绑定 | 连接成功后发送 `{"type": "bind", "userId": N}` 绑定通道 |
| 自动重连 | 断开后 3s 间隔 × 最多 5 次，指数退避 |
| 心跳检测 | 30s 间隔 ping，保持长连接 |
| 消息分发 | 基于 `messageHandlers Map`，按 `type` 字段路由到不同处理器 |
| 通知处理 | `type === "notification"` → `ElNotification` 弹窗 + 点击跳转评估结果页 |

### 5. 分片上传前端实现

`api/fileUpload.ts` 是前端最复杂的模块，完整实现了三阶段上传协议：

**阶段一：初始化上传**（`initUpload`）
- 调用 `POST /api/org/project/{projectId}/file/init`。
- 前端传参：`projectId`、`fileHash`（MD5）、`fileSize`、`totalChunks`、`fileType`。
- 后端返回 `uploadId`，前端保存用于后续分片传输。

**阶段二：分片上传**（`uploadChunks`）
- 通过 `ConcurrencyController` 并发控制器管理最多 3 个并发分片。
- 每个分片上传带重试机制（`retryAsync`，最多 3 次，指数退避）。
- 分片接口：`POST /api/org/project/{projectId}/file/chunk`（FormData，字段 `uploadId`、`chunkIndex`、`file`）。
- 实时进度回调 `onProgress` 返回 `{uploaded, total, percentage, chunkIndex}`。

**阶段三：确认上传**（`confirmUpload`）
- 调用 `POST /api/org/project/{projectId}/file/confirm`。
- 仅传 `uploadId`，后端校验分片完整性后合并，异步触发 Kafka 处理链路。

**辅助能力**：
- `calculateFileHash()`：使用 CryptoJS 分块计算文件 MD5，2MB/块，支持进度回调。
- `getFileExtension()`：从文件名提取扩展名用于类型校验。

## 十四、当前不足与改进方向

### 1. 行为抽取仍较粗粒度

当前行为抽取主要依赖 `FileScanner` 按页扫描 + `ContentExtractor` 文本片段提取，本质上是基于规则的分段方法，尚未引入 NER 命名实体识别、事件抽取等 NLP 深度技术。

**改进方向**：
- 引入 UIE/DeepKE 等信息抽取模型，识别"主体-行为-对象"三元组。
- 增加行为过滤模型，过滤不相关文本（如目录、页眉页脚、模板文本）。
- 支持表格数据的结构化提取（当前仅处理文本流）。

### 2. BERT 向量化与分类效果需要量化评估

虽然 BERT 分类（多任务 4 头输出）和向量化（768 维）服务已接入，但需要进一步补充：

- 标注数据集规模（当前训练集、验证集、测试集的样本量）。
- 各分类头的准确率、召回率、F1 指标（tags 46 类、type 2 类、dimension 6 类、industry 72 类）。
- 误检和漏检样例分析。
- 法规领域术语微调（如使用 Legal-BERT 或领域继续预训练）。

**向量化模型改进**：
- 当前 `bert-base-chinese` + CLS 向量 → 建议替换为 `BAAI/bge-base-zh-v1.5`（mean pooling + L2 归一化），预期 C-MTEB 从约 50 提升至 63+。
- 当前逐条编码 → 改为批量推理（batch_size=32），GPU 场景下可提速 5-10 倍。
- 添加 L2 归一化后处理，确保余弦相似度等价于点积。

### 3. 智能匹配可增加重排序环节

当前相似度计算（`SimilarityCalculator`）采用加权余弦相似度 + Jaccard 系数混合，为静态手工公式，无法动态学习匹配偏好。

**改进方向**：
- 在 KNN 召回 Top-200 候选后，引入 Cross-Encoder 重排序模型（如 `BAAI/bge-reranker-large`），对 Top-20 精排序，预期匹配精度提升 20%-30%。
- 重排序模型独立于向量化模型，无需改动现有嵌入管线。

### 4. 风险解释字段需要丰富

当前风险记录包含基础字段，但解释性需要增强。建议补充：

- `riskReason`：风险原因（如"得分比例仅 0.25，低于阈值 0.5"）。
- `violationClause`：违规条款依据（引用具体法规条款号）。
- `complianceSuggestion`：合规建议（整改措施）。
- `responsibleParty`：责任主体。
- `disposalMeasure`：处置措施。

### 5. 前端可视化与报告导出还需完善

后端聚合数据（`AssessmentGeneralDetails`、`IndicatorDistributionVO`、`RiskVO`）已就绪，但需要前端仪表盘对接和 PDF/Word 报告导出功能。

### 6. 部署和监控需要生产化

当前 Docker Compose 适合开发环境，生产环境需要：

## 十七、答辩问答准备

### Q1：你们的系统和普通规则匹配有什么不同？

答：

普通规则匹配主要依赖关键词或固定条件（如 `if keyword in text then risk=high`）。本系统在规则判断前加入了 **BERT 语义理解**环节：

1. 将企业行为文本通过 BERT 转为 768 维语义向量（`/encode` 接口）。
2. 在 ES/Milvus 中进行 KNN 向量召回候选指标和法规（而非关键词匹配）。
3. 计算余弦相似度 + Jaccard 系数——处理"表达不完全一致但语义相关"的文本。
4. 最后才进入定性/定量规则计算（`QuantitativeCalculator` / `QualitativeCalculator`）。

例如，"向政府官员赠送礼品卡"和"提供不正当利益给公职人员"在关键词层面不同，但在 768 维语义空间中相似度很高。

### Q2：为什么要使用 Kafka？

答：

文档解析（可能几十页 PDF）、BERT 向量化（每个行为需 100ms+）、指标计算（每个行为需匹配 200 个候选法规和指标）都可能耗时较长。如果全部放在 HTTP 请求中同步处理，会导致请求超时（HTTP 默认 30s）。

本系统通过 Kafka 将整个链路拆为 4 个异步阶段：

| 阶段 | Kafka Topic | 预估耗时 |
| --- | --- | --- |
| 文件上传 → 行为处理 | `behavior_processing_tasks` | 30s-5min |
| 行为入库 → 指标计算 | `indicator_calculation_tasks` | 1min-30min |
| 指标完成 → 报告聚合 | `assessment_completed_events` | 10s-1min |
| 报告完成 → 通知推送 | `notification_tasks` | <1s |

Kafka 配置了 3 分区 + 独立 consumer group，确保消息有序且支持并行消费。如果某个阶段处理失败，消息还在 Kafka 中，可以重新消费（手动 offset 重置）。

### Q3：为什么同时用 Elasticsearch 和 Milvus？

答：

| 维度 | Elasticsearch (8.11) | Milvus (2.3.5) |
| --- | --- | --- |
| 定位 | 全文检索 + 结构化过滤 + 向量检索 | 专业向量检索引擎 |
| 文本查询 | IK 中文分词，支持关键词+短语+模糊匹配 | 不支持 |
| 向量检索 | `dense_vector` + `cosineSimilarity` script_score | 原生 ANN 算法（IVF/HNSW），检索更快 |
| 过滤能力 | 结构化字段过滤（industry、region 等） | 标量过滤表达式 |
| 当前用途 | 行为/指标/法规数据主存储 | 知识库向量召回 |

当前系统中 ES 承担主要数据检索和落库（因为需要同时支持文本搜索和向量搜索），Milvus 用于知识库的向量召回能力建设。后续当数据量增长到百万级别时，Milvus 的 ANN 检索性能优势会更加明显。

### Q4：风险分数是怎么来的？

答：

以一次评估为例（项目有 50 条行为，需匹配 30 个指标）：

1. **候选召回**：每个行为的 768 维向量在 ES 中 KNN 搜索，召回 Top-200 候选法规和指标。
2. **阈值过滤**：行为-法规相似度 < 0.15 的过滤，法规-指标相似度 < 0.2 的过滤。
3. **权重计算**：对通过筛选的法规计算三层权重（层级权重：法律>规章>文件；时效性权重：现行>修订>废止；相似度权重：余弦值归一化）。
4. **规则计算**：定量数据走 `range_rule`（如"金额在 100-500 万之间得 60 分"），定性判断走 `binary_rule`（如"是否获得用户同意？是=100 分，否=0 分"），无规则走 `FallbackCalculator`。
5. **分数聚合**：同一指标下多个行为的计算结果取加权平均，得到最终 `calculatedScore`。
6. **风险判定**：`scoreRatio = calculatedScore / maxPossibleScore`，< 0.5 触发风险。

关键代码类：`SimilarityCalculator`、`RegWeightCalculator`、`QuantitativeCalculator`、`QualitativeCalculator`、`FallbackCalculator`。

### Q5：目前系统最大的不足是什么？

答：

主要不足在三个方面：

**第一，行为抽取还比较粗**：当前依赖 `FileScanner` + `ContentExtractor` 的规则分段，未引入 NER 命名实体识别和事件抽取模型，导致抽取的行为粒度不够细，可能混杂模板文本。

**第二，BERT 效果缺乏量化数据**：向量化使用通用 `bert-base-chinese`（非嵌入专用），分类模型虽然有 4 头输出但缺乏标注数据集的精确评估指标（准确率、F1 等），影响可信度。

**第三，风险解释字段不完整**：当前指标结果虽保留了关联行为和法规 ID，但缺少自然语言形式的风险原因、违规条款、合规建议等字段，报告的可读性有待提升。
