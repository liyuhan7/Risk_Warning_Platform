# 企业合规智能分析系统升级 · 项目计划

## 一、这次要做什么

把系统从“向量相似度匹配 + 固定规则查表”升级为“LLM + RAG + 规则引擎”的合规推理系统。

不动的部分：用户、企业、项目、通知、报告等外围模块整体保持原样，主要改造“材料进入系统之后如何形成风险”这条主分析链。

目标不是简单地“把 BERT 换成大模型”，而是重新划分职责：

- LLM 负责材料理解、事实抽取、法规适用性分析和合规差距推理；
- RAG 负责从指标库、法规库和企业证据中召回可靠上下文；
- 规则引擎负责读取既有指标规则，完成确定性评分和风险等级计算；
- 最终风险结果能够回溯到原始材料、企业事实、法规依据和判断过程。

---

## 二、为什么现在的评估结果不可用

现有问题不是单一的“语义模型不够强”，而是从事实抽取、知识召回、语义判定、规则计算到结果聚合的整条链路都存在结构性问题。

### 根因 1：Behavior 本身没有形成可靠的结构化事实

当前文档处理链生成 Behavior 时，初始只保存文本描述，`type`、`dimension`、`status`、`tags`、`quantitativeData` 等关键字段为空或默认值。

后续分类过程会补充部分类型、维度和标签，但：

- 状态没有可靠进入主抽取链；
- 定量数值没有稳定从原文中抽取；
- 原始文件、页码、字符位置等证据信息没有保留；
- 文本片段和最终 Behavior 之间缺少稳定的可追溯关系。

结果是：

> 后续评分系统拿到的并不是可靠的“企业事实”，而只是带有少量分类信息的文本片段。

这是整个评估链最底层的问题。

---

### 根因 2：召回公式严重依赖缺失数据，导致候选过滤过强

当前行为到法规/指标的相似度公式为：

```text
0.65 × 向量余弦 + 0.35 × 标签 Jaccard
```

实测数据中：

```text
行为数据 tags 为空：600 / 600
法规数据 tags 为空：2466 / 4865
```

Behavior 标签全部为空时，标签 Jaccard 恒为 0，公式实际退化成：

```text
0.65 × cosine
```

主链后续又要求：

```text
behavior → regulation similarity
×
regulation → indicator similarity
≥ 0.20
```

因此当标签和行业等辅助特征贡献不足时，两侧都需要较高的原始余弦相似度才能通过过滤。

---

### 根因 3：当前 BERT 表示并不适合作为语义检索模型

当前向量化使用 `bert-base-chinese`，直接取 CLS 向量作为文本表示。

法规文本实测平均约 48 字、中位数约 46 字，指标名称平均约 22 字，两侧都是短文本。

问题在于：

- 通用 BERT CLS 并不是专门针对语义检索训练的 embedding；
- 对短文本的相似度区分能力不足；
- 不同文本的余弦结果容易聚集在相近区间；
- 当前系统又高度依赖相似度阈值做业务判定，因此表示能力不足会被进一步放大。

需要注意：

> 当前余弦计算本身已经通过向量范数完成归一化。真正的问题是模型不是检索专用 embedding，短文本表示能力不足。

另外，法规数据本身已经接近条款粒度，因此本轮不需要额外做大规模法规切块。

---

### 根因 4：定量评分使用了错误的目标值

当前兜底逻辑将指标的 `maxScore` 当作定量业务目标值，然后和 Behavior 中的实际业务数值计算偏差。

但 `maxScore` 本质是：

> 指标的最大得分。

它不是：

> 合规要求达到的业务目标值。

例如：

```text
maxScore = 1.0
实际业务数值 = 82
```

或者：

```text
maxScore = 0.5
实际业务数值 = 6,610,000
```

拿两者计算偏差没有业务意义。

当前定量计算中，偏差率超过 1 会直接得到 0 分，因此大量定量 Behavior 会被错误压到极低分甚至 0 分。

这说明：

> 现有系统虽然保存了定量数据，但没有真正使用正确的指标计算规则解释这些数据。

---

### 根因 5：定性判断退化成固定状态查表

当前定性评分依赖：

```text
法规方向 × Behavior 状态
```

形成固定映射表。

例如：

| 法规方向 | 已完成 | 进行中 | 暂停 | 终止 |
| --- | ---: | ---: | ---: | ---: |
| 禁止 | 0.0 | 0.2 | 0.5 | 1.0 |
| 必须 | 1.0 | 0.7 | 0.3 | 0.0 |
| 可选 | 0.9 | 0.7 | 0.6 | 0.5 |

实测现有 600 条行为状态主要集中在：

```text
进行中
已完成
```

因此实际大量评分只会落到少数几个固定值上。

更关键的是：

> 评分过程几乎不理解 Behavior 描述本身表达了什么，只看“状态”和“法规方向”。

所以两段完全不同的企业行为，只要状态相同、匹配法规方向相同，就可能得到相近甚至完全一致的评分。

---

### 根因 6：821 条指标既有规则没有真正进入主计算链

指标数据本身已经包含：

```text
calculation_rule
risk_rule
```

包括二元规则、区间规则、风险阈值等。

但当前主链没有让这些规则真正决定 IndicatorResult 和 Risk。

实际流程仍然主要依赖：

```text
相似度
→ 法规方向/行为状态打分
→ 加权平均
→ IndicatorResult
```

最终风险生成阶段又统一使用：

```text
scoreRatio < 0.5
```

作为风险触发条件。

也就是说：

> 数据库里已有的指标计算规则和风险规则，与实际风险计算主链处于脱节状态。

因此本轮规则引擎的主要工作不是重新设计 821 条规则，而是把已有规则真正接回评估流程。

---

### 根因 7：系统实际上没有真正的合规推理能力

虽然仓库中存在 LLM 工具类，但它主要用于标签、类型、状态等辅助推断和测试，并没有进入当前风险评估核心业务链。

现有主链实际还是：

```text
相似度
+
固定阈值
+
固定映射表
+
加权平均
```

没有真正完成以下问题：

```text
这条法规是否适用于当前企业？
法规要求的合规条件是什么？
企业材料实际上证明了什么？
企业事实与法规要求之间差在哪里？
这是明确违规、潜在风险，还是证据不足？
```

因此目前系统更接近：

> 语义匹配辅助的规则评分系统。

还不能称为真正的“智能合规风险分析”。

---

### 根因 8：风险结果缺少证据链，且结果聚合存在边界问题

当前 Risk 中已经设计了法规、违规类型、合规要求、影响范围、整改建议等字段，但多个关键字段实际仍为空值。

因此最终风险无法回答：

```text
为什么产生这个风险？
依据哪段企业材料？
对应哪条法规？
法规具体要求什么？
企业实际情况是什么？
哪里构成了合规差距？
```

同时当前风险汇总逻辑在“一个风险都没有”的情况下存在边界异常，可能将空风险集合进一步传入风险等级计算，导致最终等级失真。

这说明结果层不仅缺解释性，也存在需要单独修复的业务逻辑问题。

## 三、问题归因总结

当前问题可以归纳为五层。

| 层次 | 当前问题 | 升级方向 |
| --- | --- | --- |
| 事实层 | Behavior 没有可靠抽取状态、数值和证据 | EvidenceChunk + LLM Fact Extraction |
| 召回层 | 标签缺失、通用 BERT CLS 区分度不足、复合阈值过滤过强 | Retrieval Embedding + RAG + 企业背景过滤 |
| 推理层 | 用相似度和状态常量表代替真正合规判断 | LLM Applicability + Gap Analysis |
| 计算层 | `maxScore` 语义误用，既有 CalculationRule / RiskRule 未执行 | Rule Engine 接入既有规则 |
| 结果层 | 风险统一阈值、聚合边界问题、证据链为空 | 确定性风险生成 + Evidence Chain |

本轮升级不是单纯替换一个模型，而是在分别修复这五层职责。

## 四、目标业务链

所有任务围绕这一条链。

```text
企业材料上传
     ↓
文档解析
     ↓
EvidenceChunk
保留原文、页码、字符位置
     ↓
LLM 事实抽取
     ↓
Structured Behavior
主体 / 行为 / 对象 / 状态 / 时间 / 数值 / 置信度
     ↓
RAG 检索
带企业背景过滤
     ├── Indicator 候选
     └── Regulation 候选
     ↓
LLM 合规推理
     ↓
AnalysisResult
适用性 / 合规差距 / 严重度 / 置信度 / 理由
     ↓
Rule Engine
读取既有 CalculationRule / RiskRule
     ↓
IndicatorResult
     ↓
Risk
     ↓
Report / Frontend
证据 + 法规 + 原因 + 建议
```

核心分工原则：

> LLM 判断“企业做了什么、法规要求什么、两者差在哪里”，规则引擎负责“怎么计算指标分数、是否触发风险、风险属于什么等级”。

这条边界同时也是系统控制大模型不确定性的核心设计。

## 五、六个核心改动方向

| # | 方向 | 原来 | 改造后 |
| --- | --- | --- | --- |
| 1 | AI 能力 | BERT 向量化 + 相似度 | Embedding + LLM 的统一 AI 能力 |
| 2 | 材料理解 | 文本片段直接成为 Behavior | Document → EvidenceChunk → Structured Behavior |
| 3 | RAG 检索 | 向量直接 Top-K | 检索专用 Embedding + 企业背景过滤 + 候选召回 |
| 4 | 风险分析 | 相似度和阈值决定关系 | RAG 找候选，LLM 判断适用性与合规差距 |
| 5 | 规则计算 | 固定状态表 + 统一风险阈值 | 接线既有指标规则，确定性计算 IndicatorResult 和 Risk |
| 6 | 可解释结果 | 风险名 + 等级 + 分数 | 原文证据 + 法规依据 + AI 判断 + 置信度 + 整改建议 |

其中：

> 2、3、4 是智能能力升级的核心；5 是保证风险结果确定性和业务可信度的关键。

三个明确的省力点：

- 821 条指标规则已经存在，本轮主要是接线和校正规则输入，不是从零设计。
- 前端已经有部分证据链和法规展示结构，可以优先补齐后端数据。
- 法规数据已经接近条款粒度，本轮无需再做复杂法规切块。

按照纵向能力划分，不按照微服务平均拆分。

协作原则：

```text

        ↓
B：让推理结果进入确定性风险计算
        ↓
C：让最终结果能够被用户理解和验证
```

三个人必须并行开发，通过第一阶段冻结的公共接口解耦。

## 八、第一阶段共同工作

### 1. 完成数据与代码基线

把当前已经发现的问题整理成固定基线：

- Behavior tags 缺失情况；
- Behavior 状态分布；
- 定量 Behavior 分布；
- 指标规则数量和类型；
- 法规文本长度；
- 当前 Risk 分布；
- 当前召回效果和风险判断效果。

这些数据既用于后续技术决策，也用于最终答辩说明：

> 为什么我们必须重构原系统。

---

### 2. 冻结公共协议

第一阶段需要共同确定：

```text
EvidenceChunk
StructuredBehavior
RetrievalResult
RiskAnalysisContext
AnalysisResult
```

其中 `AnalysisResult` 是三个人最关键的共同接口。

A 负责产生它；

B 负责让 Rule Engine 消费它；

C 负责将其中的解释信息展示给用户。

---

### 3. 保留旧系统作为 Baseline

在替换旧分析链之前保留当前版本的评估结果。

后续需要能够对比：

```text
旧系统
BERT + 相似度 + 固定规则

vs

新系统
LLM + RAG + Rule Engine
```

重点比较：

- 指标召回；
- 法规召回；
- 风险判断；
- 错误案例；
- 可解释性。

---

### 4. 修复会污染基线的明显业务 Bug

在正式记录旧系统基线前，只修复会导致统计结果明显失真的确定性 Bug。

例如：

- 风险结果聚合的空集合边界问题；
- 已确认的分数计算实现错误。

不在这一阶段尝试继续“调好”旧 BERT 主链。

---

### 5. 完成必要的安全和架构清理

包括：

- 吊销并替换仓库中曾硬编码的大模型 API Key；
- 清理测试脚本中的敏感 Token；
- 确认向量检索统一以 Elasticsearch 为主；
- 不再同时维护无实际主链价值的重复向量基础设施。

## 十、技术方向

| 项目 | 当前决定 |
| --- | --- |
| 大模型 | 使用统一 LLM Provider 接入，优先验证结构化输出稳定性 |
| Embedding | 换成检索专用中文模型，避免继续直接使用通用 BERT CLS |
| 检索存储 | Elasticsearch 作为主检索基础设施 |
| 企业背景 | 行业、地域、面向对象、企业基本信息进入 Retrieval Filter 和 LLM Context |
| 法规数据 | 当前已经接近条款粒度，不额外做复杂切块 |
| 指标规则 | 优先复用现有 CalculationRule / RiskRule |
| 风险决策 | LLM 不直接决定最终分数，规则引擎负责确定性计算 |
| 结果解释 | 每个 Risk 必须能够回溯 Evidence、Behavior、Indicator、Regulation |

## 十一、风险与决策点

| 时间 | 检查内容 | 不达标处理 |
| --- | --- | --- |
| 8/17 | 根因和公共契约是否冻结 | 立即减少非核心改造，优先锁定主链 |
| **8/31** | **端到端垂直切片是否跑通** | 砍掉所有 P1，优先完成主链 |
| 9/14 | LLM + Rule Engine 是否能输出真实风险结果 | 前端功能收缩，只保证核心结果展示 |
| 9/24 | 整个系统是否可以完整运行 | 停止新增功能，进入测试与 Demo 固化 |

最大风险不是某一个模型效果不好，而是：

> 到九月中旬三个人仍然在分别开发模块，却没有真正跑通过端到端链路。

因此所有阶段都以“完整垂直切片是否可运行”为最重要的检查标准。

第二个主要风险是 LLM 输出不稳定，因此从设计阶段就需要保证：

```text
LLM 输出结构化结果
→ 校验
→ Rule Engine
```

而不是让 LLM 自由生成最终风险分数。

## 十二、最终交付目标

系统至少要能够证明：

1. 能从企业上传材料中保留并定位原始证据；
2. 能从材料中抽取真正参与评估的结构化企业事实；
3. 能结合企业背景检索相关指标和法规；
4. 能通过 LLM 分析法规适用性和企业合规差距；
5. 能真正执行已有指标计算规则和风险规则；
6. 最终风险不是由固定相似度和状态查表直接决定；
7. 每个 Risk 都能解释“企业做了什么、法规要求什么、为什么构成风险”；
8. 能在前端展示原文证据、法规依据、AI 判断和整改建议；
9. 能用固定测试集证明新版链路相比旧版评估结果明显改善；
10. 整个流程能够从前端上传材料一直运行到最终风险报告。

## 十三、项目升级的核心表述

本次升级不是简单从 BERT 换成 LLM，而是：

> 对原有风险评估链进行职责重构：以 EvidenceChunk 和结构化事实解决输入可靠性，以 RAG 解决指标和法规召回，以 LLM 解决法规适用性和合规差距推理，以既有 Rule Engine 解决确定性评分和风险等级计算，最终建立能够回溯原始材料和法规依据的可解释风险评估链路。

最终形成：

```text
Evidence
→ Fact
→ Retrieval
→ Reasoning
→ Rules
→ Risk
→ Explanation
```

这就是需要完成的核心升级。
